# Детекция подключения/отключения дрона на RC2 — результаты живого исследования

**Железо:** DJI RC 2 (`rc331`, Android 11) + Lito X1 (`1581EXAMPLE000000000`).
**Дата:** 2026-08-13. **Инструмент:** diag-server `http://<rc-ip>:8899/`.
**a11y:** включён (`DjiFlyAccessibilityService`, `serviceOn:true`) на протяжении всех замеров.

Цель — определить, какими сигналами можно надёжно детектировать факт **линка дрона с пультом** в
матрице состояний: наш апп на переднем плане/в фоне; DJI Fly на переднем плане / в фоне / остановлен;
с accessibility-сервисом и без. Активные запросы на шине разрешены; работа при остановленном Fly —
желательна.

> TL;DR. Единственный **пассивный** признак линка — **живой FLYC-OSD поток на порту 40007** (не сам
> факт трафика, а его объём/тип). Порт **40009 не различает** дрон on/off (это housekeeping пульта), из-за
> чего текущий `LinkState.connected()` даёт **постоянный false-positive «подключён»**. Активный признак —
> **реальный `00:51`-ответ** аппарата (не закешированный `51:14`-бродкаст). Оба живут на 40007 и
> **не зависят от DJI Fly** (работают даже когда Fly остановлен), но конкурируют с видео Fly, когда тот
> на переднем плане. Accessibility даёт надёжно только **какой апп на переднем плане**; состояние связи
> Fly рисует **графически**, поэтому a11y-скрейп для *connect* ненадёжен.

## 1. Карта портов loopback

| Порт | Что несёт | Открыт без дрона? | Различает дрон on/off? |
|---|---|---|---|
| **40009** | SDR/радио + housekeeping пульта (`00:81`, `06:AE`, `06:A4`, `06:77`) | **Да** (всегда) | **Нет** — поток идентичен on/off |
| **40007** | FLYC-OSD / видео-миррор Fly (wrapped `55 cc 30 75`) | Да, но только housekeeping + кешированный `51:14` | **Да** — по объёму/наличию живого OSD |
| 40008 | FLYC param inject | Да | не проверялось пассивно (порт для записи) |
| 8901, 8902 | служебные | Да | — |

**Факт:** порты 40009/40008/40007/8901/8902 открыты **при выключенном дроне и остановленном Fly** →
прокси **системные**, не хостятся приложением Fly и не появляются/исчезают по линку. Значит скан порта
(`/ports`) — **не** индикатор связи.

---

## 2. Что на самом деле течёт по 40009 (главный native-канал)

`/connect` всегда садится на **40009**. Пассивная телеметрия там (`/radiolink`):

```
Дрон OFF, Fly stopped:  00:81 "rc331" (~0.3 Гц),  06:AE p=0000010000000400040004000400040004 (~10 Гц)
Дрон ON,  Fly stopped:  ТЕ ЖЕ 00:81, 06:AE — payload 06:AE БАЙТ-В-БАЙТ идентичный
Дрон ON,  Fly foreground: +00:82 (реакция на Fly), 06:AE тот же
```

`00:81`/`00:82` payload = `72 63 33 33 33 31…` = ASCII **"rc331"** — это идентификатор **самого пульта**.
`06:AE` — радио-housekeeping пульта, идёт всегда. **Ни один байт 40009 не флипается при линке дрона.**

### ⚠️ Дефект `LinkState`

`LinkState.connected()` считает линком **любой** входящий кадр
([LinkState.kt:51](../app/src/main/java/com/dji/fccgpsoff/LinkState.kt#L51)). Но канал сидит на 40009,
который льёт housekeeping **без дрона** → `/link` возвращает `{"connected":true}` **при выключенном
дроне**. Проверено: дрон OFF → `/link connected:true, ageMs<1000`. Это ломает гейт `awaitLink` в
keepalive ([FccKeepaliveService.kt:119](../app/src/main/java/com/dji/fccgpsoff/FccKeepaliveService.kt#L119)):
он «видит аппарат» там, где его нет.

`HomePointMonitor` (03:44) при этом видит **0 кадров** — FLYC-OSD на 40009 не приходит, поэтому
home-point-триггер на главном канале **никогда не срабатывает** (подтверждает комментарий в коде keepalive).

## 3. Что течёт по 40007 (реальный источник признаков дрона)

| Состояние | Объём `/cap?port=40007&ms=3000` | Содержимое |
|---|---|---|
| Дрон **ON** (Fly stopped) | **~80 КБ / 3 с** | Плотный разнотипный FLYC-OSD: `03:xx`, атитьюд, множество cmdSet |
| Дрон **OFF** | **~9 КБ / 3 с** | Только `51:04`/`51:14` (кеш. serial), `0e:66`, `06:AE` — housekeeping |

**Вывод:** дискриминатор — **не наличие трафика** (он есть всегда), а **тип живого OSD**. 40007-поток
**не зависит от Fly**: при остановленном Fly дрон-ON поток так же плотный — значит OSD выкладывает
системный прокси, а не сам Fly.

### Сигнатура живого линка (разбор дрон-ON потока, 771 inner-кадр / 3 с)

| cmdSet:cmdId | ~Гц | присутствует при дрон-OFF? |
|---|---|---|
| **`23:B2`** | **50** | нет |
| `04:05` | 20 | нет |
| `03:43`, `03:53`, `22:21`, `22:AD`, `22:20`, `0A:5A`, `0A:BC`, `02:80`, `08:66` | 10 | нет |
| `03:09`, `24:71`, `00:F1`, `21:06`, `23:A1` | 3–7 | нет |
| `06:AE`, `51:04`, `51:14`, `0E:66` | 5–9 | **да** (housekeeping + кеш) |

При дрон-**OFF** поток = **только** `06:AE`/`51:04`/`51:14`/`0E:66`. → **Самый дешёвый порог «живой линк»
= присутствие любого high-rate FLYC-OSD, например `23:B2`@50 Гц или `03:43`@10 Гц.** Заметь: `03:44`
(который слушает `HomePointMonitor`) в топе **нет** — в помещении home-point не записан; `03:43` как
маркер линка надёжнее.

**Нюанс кеширования (Q-B1, проверено во времени):** после выключения дрона пульт **продолжает вещать
`51:14` с serial последнего аппарата**. Объём 40007 спадает лестницей `ON ~80 КБ → OFF сразу ~9 КБ →
OFF минуты ~1 КБ / 3 с`, но `51:14` жив **минимум минуты**. Поэтому «на 40007 виден serial» — **не**
признак живого линка; порог по объёму ненадёжен (OFF-базлайн сам плывёт) — ключиться надо на **тип**
OSD-кадра, не на байты.

## 4. Активные запросы

| Запрос | Дрон OFF (холодный) | Дрон ON | Дрон OFF (после линка) | Годен как признак? |
|---|---|---|---|---|
| `00:51` serial (40007) | «no serial» | **вернул serial** | **всё ещё вернул** (кеш `51:14`) | Только если требовать **реальный `isResponse`-ответ**, а не regex по окну |
| `07:19` country (40009) | no reply | no reply | no reply | ❌ никогда не роутится |
| `03:F8` param read (**40008**) | no answer | no answer | no answer | ❌ не роутится — **но см. поправку ниже** |
| `00:01` deviceinfo | — | подхватил случайный кадр | — | ❌ ненадёжно |

> **Поправка от 2026-08-14.** Строка `03:F8` выше относится к **порту 40008**, и там она верна:
> окно чтения на 40008 отдаёт **ноль кадров** — это чистый sink на запись. На **40007 wrapped**
> чтения параметров **возвращаются**: при DJI Fly в фоне одно окно 1500 мс отвечает примерно в
> **70%** случаев (при остановленном Fly — почти всегда). Там же отвечают `03:F7`, `03:E0` и
> `03:E1`. Это закрывает открытый вопрос, записанный в шапке `ParamRead`. Потери **пооконные, а
> не покадровые**: за 24 окна с 2 и 3 запросами не встретилось ни одного частичного результата.
> Подробности и таблицы — [config-table-commands.md](config-table-commands.md).

`AircraftSerial.read()` — **живой** запрос (шлёт `00:51`, читает окно 400 мс, до 3 попыток), но
`extract()` в фолбэке ловит **любой** ASCII-serial в окне, включая кешированный `51:14`-бродкаст
([AircraftSerial.kt:109](../app/src/main/java/com/dji/fccgpsoff/AircraftSerial.kt#L109)). Для чистого
live-признака нужно требовать именно `fr.cmdSet==0x00 && fr.cmdId==0x51 && fr.isResponse`.

**Только `00:51` роутится обратно** (serial — задокументированное исключение); country/param-reads/
deviceinfo владельцем реплаев (Fly) к нам не приходят. При **остановленном Fly** serial роутится так же
(владельца сессии нет — конкуренции меньше).

## 5. Роль accessibility

- **Foreground-пакет — надёжно.** `/foreground` верно различал: `com.example.dumlfcc` (self,
  `readsAllowed:true`) ↔ `dji.go.v5` (`flyForeground:true`, `readsAllowed:false`). Это основа
  `ForegroundGate`.
- **Скрейп связи с экрана Fly — ненадёжно.** При Fly на переднем плане и живом дроне `/identity` дал
  `drone:null`: на лётном HUD **нет имени модели** (оно только на экране подключения). Скриншот
  ([assets/fly-hud-drone-connected.png](assets/fly-hud-drone-connected.png)) показывает, что связь
  отображается **графически** (шкала сигнала, иконка RC, живой FPV, заряд), текстом — лишь «Режим N» и
  предупреждение про GPS. → a11y-скрейп годен максимум для ловли **disconnect-баннера** («Отключено»/
  «Нет сигнала»), и то локализованного/версионно-хрупкого.
- **Без a11y:** теряем foreground-детекцию (гейт «слепнет», `readsAllowed` по умолчанию true) и
  UI-скрейп. Плюс a11y-сервис держит наш процесс живым — это можно использовать как хост для пассивного
  слушателя (см. §7).

## 6. Матрица «состояние → рабочий детектор»

Дрон **ON**. P = основной, ✓ = доступен, ⚠ = ценой блипа видео Fly, ✗ = не работает.

| Наш апп | DJI Fly | 40009 pass (LinkState) | 40007 pass (OSD-объём) | active `00:51` | a11y foreground | a11y connect-скрейп |
|---|---|---|---|---|---|---|
| Передний | Остановлен | ✗ (всегда true) | **P** (Fly-незав.) | ✓ (роутится) | self | — (нет UI) |
| Передний | Фон | ✗ | **P** | **P** (gate открыт) | self | — |
| Фон (FGS) | Передний | ✗ | ⚠ (блип) | ⚠ gate блокирует | dji ✓ | disconnect-only, хрупко |
| Фон (FGS) | Фон | ✗ | **P** | ✓ | self/other | — |
| Фон (FGS) | Остановлен | ✗ | **P** (Fly-незав.) | ✓ | self | — |
| Процесс мёртв (нет FGS/экрана) | любой | ✗ | ✗ | ✗ | ✗ | ✗ |

Ключевые следствия:
- **40009/LinkState не детектирует дрон ни в одной ячейке** — требует фикса (§2).
- **40007-OSD** — единственный пассивный детектор, работает **везде, включая Fly stopped**, но при
  **Fly foreground** возмущает видео.
- **Fly foreground** — единственная проблемная колонка: оба надёжных признака (40007-OSD, `00:51`) стоят
  блипа видео; бесплатного текстового a11y-признака *connect* нет.

## 7. Рекомендации (без изменения байтов/CRC/портов)

1. **Починить `LinkState` (приоритет).** «Любой RX = линк» ложно. Варианты:
   (а) кормить `LinkState` только кадрами **с 40007** (aux-reader), фильтруя живой OSD (например `03:xx`
   high-rate), а не housekeeping; либо (б) на 40009 завести whitelist cmdSet:cmdId, который реально
   меняется при линке (по данным §2 такого на 40009 **не найдено** — поэтому (а) предпочтительнее).
2. **Пассивный детектор линка = aux-reader на 40007 + распознавание живого OSD** (частота/тип кадров,
   а не факт сокета и не кешированный `51:14`). Кормить `HomePointMonitor`/`LinkState` именно оттуда.
   Гейтить активность порогом: включать aux только когда `ForegroundGate.isFlyForeground == false`
   (иначе блип видео) — либо принять кратковременный блип по явному запросу.
3. **Активное подтверждение = «реальный `00:51`-ответ»** (`isResponse`), а не regex-фолбэк по `51:14`.
   Тогда «serial есть» перестаёт быть false-positive после отключения дрона.
4. **Ячейка Fly-foreground:** честно признать, что zero-cost connect-детекции нет. Дефолт — не трогать
   40007 (беречь видео), полагаться на последний известный статус + опциональный a11y disconnect-баннер;
   для точной проверки — один `00:51` по требованию пользователя (с предупреждением о блипе).
5. **Резидентность в фоне:** держать пассив живым через FGS **или** через уже включённый a11y-сервис
   (он живёт в нашем процессе и перезапускается системой) — можно поднимать aux-reader в
   `onServiceConnected`.

# Fly stopped, дрон ON

# Fly FOREGROUND, дрон ON
/foreground   -> {"foreground":"dji.go.v5","flyForeground":true,"readsAllowed":false,"serviceOn":true}

# Fly BACKGROUND, дрон ON

/serial       -> 1581EXAMPLE000000000            # роутится
/country,/readparams,/deviceinfo -> no route

# Fly background, дрон OFF (после линка)
/serial       -> 1581EXAMPLE000000000            # кешированный 51:14, НЕ live
/cap 40007    -> ~9 КБ/3с, только 51:04/51:14(serial)/06:AE
/link         -> connected:true                  # 40009 housekeeping не прекращается

## Приложение B. Открытые вопросы — ЗАКРЫТЫ замерами

- **Q-B1 (кеш 51:14):** 40007 **не замолкает** после выключения дрона. Объём спадает лестницей
  `ON ~80 КБ → OFF сразу ~9 КБ → OFF минуты ~1 КБ / 3 с`, но `51:14` с serial последнего аппарата
  вещается **минимум минуты**. → порог по объёму ненадёжен; ключиться на **тип** OSD-кадра.
- **Q-B2 (политика vs прокси при Fly foreground):** гейт — **чистая политика**. При выключенном a11y
  (`readsAllowed:true`) `/serial` и `/send` на 40007 **читаются нормально при работающем Fly** — прокси
  роутит/вещает независимо от foreground. НО цена подтверждена **визуально**: серия чтений 40007 при Fly
  на переднем плане дала **фриз видео 1–2 с + обнуление статус-строки Fly (время полёта пусто, уровень
  сигнала пусто красным), восстановление через 1–2 с.** → `ForegroundGate` обоснован: 40007 при активном
  Fly трогать нельзя.
- **Q-B3 (дешёвый порог линка):** найден — присутствие high-rate FLYC-OSD на 40007 (`23:B2`@50 Гц или
  `03:43`@10 Гц), которых при дрон-OFF нет. См. таблицу сигнатуры в §3.

### Минимальное чтение 40007 — «мягкого» касания НЕТ (замерено)

Гипотеза: одиночный касательный запрос (`/send port=40007 read=0`, open→write→close за единицы мс) не
успеет прервать видео. **Опровергнута:** даже **один** такой запрос при Fly на переднем плане даёт
**фриз видео ~1 с + обнуление статус-строки** (время полёта/сигнал), т.е. полный разрыв, не частичный.
→ блип вызывает **сам факт открытия competing-сокета на 40007**, а не длительность
окна чтения. **Вывод: любого касания 40007 при активном Fly достаточно для ~1 с разрыва картинки** —
включая aux/hijack-reader (это тоже второй сокет на 40007). Пассивная детекция дрона через 40007 при
Fly на переднем плане несовместима с гладким видео **в принципе**. Порт 40009 (наш постоянный канал)
при этом **не блипает никогда** — весь сеанс он был открыт без эффекта на Fly.

### Ветка a11y = OFF (замерено)

- `/foreground` → `serviceOn:false`, `flyForeground:false` (значение foreground **замерзает** на последнем,
  что видел a11y), `readsAllowed:true` → **гейт слепнет, чтения всегда разрешены**. Значит без a11y защита
  видео Fly **не работает** — приложение будет читать 40007 даже когда Fly на переднем плане (→ блип).
- `/identity` → `drone:null` (нет скрейпа модели). RC по-прежнему определяется из системных пропсов.
- Практический вывод: **a11y выключать нежелательно** — он и есть источник foreground-гейта, без него
  теряется единственная защита от блипа видео.

## Приложение C. Брокер 40009 не держит постоянного клиента (замерено 2026-08-18)

Постоянное соединение с `127.0.0.1:40009` **закрывается самим брокером** через
секунды после подключения, хотя мы в этот сокет ничего не пишем (все отправки идут
отдельными one-shot сокетами). Старый код запускал читателя один раз и позволял
потоку умереть, а падение замечал только 30-секундный health-check в Kotlin.

Замеры на RC 2 (rc331) + Lito X1, DJI Fly 1.21.8:

| | до супервизора | после |
|---|---|---|
| кадры на main-канале | **20 за 10 минут** (0.03/с) | **9.7/с** |
| `connected` в `nativeStats` | 0 почти всегда | 1 |
| «main RX channel down» в логе | каждые ~31 с | 0 |
| переподключения | — | 8.9/мин, бэкофф 200 мс → простой 3.0% |

Причина обрыва — счётчик `mainDrop` в `/stats`: **всегда `0`**, то есть `recv()`
вернул 0 = штатное закрытие со стороны пира. Не сброс, не ошибка, не наш баг.

Длина окна (`mainWindowMs`) **плавает**, в наблюдённом диапазоне ~2–6 с:

```
2004, 2006, 2006          ← сессия 1, пока шли bootstrap-бурсты FCC (каждые ~14 с)
6038, 6037, 6037, 6038    ← сессия 1, после того как бурсты прекратились
3894, 3830, 3829          ← сессия 2, установившийся режим
2025, 12095, 2012, 2015   ← сессия 3, канал поднят вручную через /connect
```

Разброс в итоге ~2–12 с. Значение 12095 мс получено уже после демонтажа, когда
на порт вообще ничего не шло, кроме опроса страны — ещё одна гиря против любой
теории фиксированного таймаута.

⚠️ По первой сессии казалось, что значений всего два (~2.005 и ~6.037 с) и что
они переключаются вместе с нашим собственным трафиком. Вторая сессия дала ~3.83 с
и эту гипотезу о квантовании сняла — окно просто переменное.

### Выселяют ли нас собственные one-shot сокеты — НЕТ (замерено)

Прямая проверка: посчитать за одно окно переподключения main-канала и наши
собственные one-shot подключения к 40009 (опрос страны `07:19`). Если выселяем
себя сами, частоты должны совпасть.

```
за 92 с:  переподключений 44 → 73 = 29  (18.9/мин)
          опросов страны   6 → 24 = 18  (11.7/мин)
          кадров         715 → 1415 = 700 (7.6/с), connected=1 во всех 10 точках
```

29 против 18 — **не совпадает**, и доминирующее окно 3.83 с не бьётся с периодом
опроса 5.1 с. Гипотеза снята. В одной точке зафиксировано `mainWindowMs=69` при
скачке `epoch` на 6 за интервал: брокер умеет разрывать соединение и через 69 мс
после accept — похоже на конкуренцию за слот с другим клиентом.

Практическое следствие: раз обрыв всегда штатный, бэкофф после него снижен с
200 мс до 30 мс (`kMainCleanCloseBackoffUs`) — при ~19 обрывах в минуту прежние
200 мс теряли ~6% потока впустую. Полный бэкофф оставлен для реальных ошибок
`recv()` и для случая, когда порт вообще не принимает.

Практический вывод: тот же самовосстанавливающийся супервизор, что давно работает
для aux/40007 («a live connection gets evicted after a burst, so re-acquire it»),
применён к main-каналу — `Transport::Impl::main_supervise` в `native/duml_core.cpp`.
Именно из-за его отсутствия aux в одной сессии набрал 908 кадров против 20 у main.
Частота переподключений того же порядка, что и одно применение FCC, которое
открывает ~45 коротких сокетов на этот же порт за 1.6 с.


### Решение: постоянный main-канал демонтирован (2026-08-18)

Полный трейс потребителей кадров route 0 (11 штук) показал, что канал держали
ради никого:

| Потребитель | Нужен route 0? | Почему |
|---|---|---|
| `DumlCapture` | **да** | единственный; байт-в-байт запись 40009, но только при включённом захвате |
| `DroneLink` | нет | первой строкой `if (route != AUX_ROUTE) return` |
| `HomePointMonitor` | нет | `03:44` на 40009 не приходит никогда — 0 кадров (раздел 2) |
| `SerialSniffer`, `ModelSniffer`, `AircraftIdentity` | нет | их носители (`51:04/51:14`, `00:01`) живут только на 40007 |
| `LinkState` | нет | документированный ложноположительный (см. «Дефект LinkState») |
| `RadioLinkMonitor` | нет | завершённый эксперимент с отрицательным результатом |
| `DiagLog.rxFrame` | нет | 5 различных ключей на route 0, дальше только шум |
| `DumlNative.observer` | нет | объявлен, никогда не присваивается |
| нативный `request()`/`send()` | нет | `nativeRequest`/`nativeSend` **не имеют вызывающих** |

Канал держался сам за себя: `awaitProxy` брал ref, а `mainChannelUp()` +
30-секундный health-check существовали, чтобы воскрешать канал, который никто не
читает. При этом вопрос там был только «брокер доступен?», и на него точно
отвечает `nativeProbePort` (connect+close, без удержания сокета).

Что сделано:
- `awaitProxy` → `probeProxy()`: connect+close по списку 40009/40008/8901-8904
  (40007 исключён — пробинг блипает видео Fly);
- `mainChannelUp()` и health-check удалены;
- `DumlCapture.start/stop` берёт и отпускает `DumlTransport` — теперь канал
  поднимается только под захват (ровно как он уже делал для aux-читателя).

**Проверено на железе 2026-08-18** (сессия 3):

```
базово       rx=0    connected=0   /link connected:false   mainReconnects=0  mainDrop=-1
/connect     rx: 0 → 305 (~11/с)   connected=1   /link connected:true   mainDrop=0
/disconnect  rx замер на 305       connected=0   /link ageMs растёт: 5.6 → 11.1 → 16.7 с
```

Старт keepalive через новый гейт: `keepalive: DUML broker reachable on 40009`
через 12 мс после старта, FCC применился через секунду по подтверждению OSD.

⚠️ **Как читать `/stats` после этого.** `connected=0` и неподвижный `rx` —
теперь **норма**, а не поломка: постоянного сокета нет by design. Канал
поднимается на время `/capstart` и на ручной `/connect`. Супервизор
`main_supervise` остаётся и работает в эти окна.
