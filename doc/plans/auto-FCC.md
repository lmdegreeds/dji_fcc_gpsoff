# План: авто-отправка полного пакета FCC в момент реального подключения дрона

## Context (зачем это)

Пользователь хочет, чтобы полный пакет FCC (`Features.applyFcc()` = `fcc.json` 21 кадр ×2
раунда + регуляторная запись) отправлялся **автоматически в момент, когда дрон подключился
к пульту — но не раньше**.

Сейчас такой авто-путь уже частично есть: `FccKeepaliveService` в режиме `HOME_POINT`
делает `awaitProxy()` → **bootstrap `applyFcc()`** → затем пере-применяет по фронту бита
home-point (03:44) с полом 30 с. Но **триггер первой отправки слабый**: `awaitProxy`
считает связь установленной, как только *любой* из портов `40009/40008/8901–8904` принял
TCP-коннект. Разбор референсов подтвердил, что это ненадёжно:

- **FreeFCC** — ровно этот «подбор по открытому порту» + слепой ре-сенд каждые 2 с; именно
  его комментарий в нашем `FccKeepaliveService` называет заменённым.
- **djiparam/MINIAPP** (`Duml.probe()`) прямо предупреждает: на `rc331` порт `40009`
  принимает коннект и **молча выбрасывает кадры** — открытый порт даёт ложное
  «подключено». Его настоящий признак живости — `isUp()` = недавний входящий кадр (RX за
  последние ~4 с), а не факт открытого сокета.
- Альтернативный подход — привязывать применение к version/identity-обмену после открытия транспорта.

Вывод: «дрон подключён» на RC2 надёжно определяется тем, что **по loopback реально идёт
телеметрия device→app** (03:44 стримится всё время, пока дрон на линке; инжектируемые
чтения назад не маршрутизируются, поэтому опираться надо на пассивный поток, а не на ответ
на запрос). Правим триггер именно на это.

## Выбранное поведение (подтверждено пользователем)

1. **Сигнал связи:** ждать реальную телеметрию дрона (входящие кадры по RX), а не открытый порт.
2. **Режим:** один раз на каждый (пере)линк + оставить существующий keepalive (пере-применение).
3. **Вооружение (arm):** запуск приложения + загрузка пульта — через уже существующий
   переключатель авто-старта keepalive и `BootReceiver` (новый флаг не заводим).

Инвариант (проверен на железе, **не меняем**): байты кадров/CRC/тайминги/порты/`fcc.json`.
Правки — только логика триггера/гейтинга + один пассивный счётчик в RX-приёмнике.

## Изменения по файлам

### 1. Новый файл `app/src/main/java/com/dji/fccgpsoff/LinkState.kt`
Пассивный трекер живости линка (аналог `djiparam` `isUp()`), в стиле `HomePointMonitor`/
`ForegroundGate` (чистый Kotlin, юнит-тестируемый).

- Поля: счётчик входящих кадров (`AtomicLong`), `lastRxMs`, и «поколение линка» для детекта
  реконнекта.
- `fun onFrame()` — вызывается из RX-приёмника на каждый доставленный кадр; инкремент
  счётчика + штамп `lastRxMs`.
- `fun connected(staleMs: Long = STALE_MS): Boolean` — `lastRxMs != 0 && now - lastRxMs < staleMs`
  (по умолчанию `STALE_MS = 4000`, как у djiparam). Это и есть «телеметрия дрона идёт».
- `fun reconnectedSince(mark): Boolean` / хелпер, дающий фронт «был застой RX → снова пошёл»
  для детекта нового линка (см. п.2 keepalive).
- `val frames`, `fun ageMs()`, `fun statusJson()` — для диагностики.
- Для тестируемости — сеам часов: `var clock: () -> Long = System::currentTimeMillis`
  (как ForegroundGate опирается на `System.currentTimeMillis`, но здесь нужен детерминизм в тестах).

### 2. `DumlNative.kt` — подключить трекер к RX-приёмнику
В `onNativeFrame(...)` (fan-out, где уже `SerialSniffer/ModelSniffer/HomePointMonitor.offer`)
добавить первой строкой `LinkState.onFrame()`. Кадры сюда приходят уже после native-фильтра
эхо/дублей (см. README «RX sink drops echoes»), значит это подлинный трафик устройства —
корректный признак живости.

### 3. `FccKeepaliveService.kt` — гейт первой отправки + пере-применение на релинк
- **Гейт «дрон реально на линке»** — новый `awaitLink(features)`: после `awaitProxy()` опрашивать
  `LinkState.connected()` каждые `WATCH_TICK_MS`; если телеметрии нет дольше `HEALTH_CHECK_MS`,
  повторно вызвать `awaitProxy()` (пере-биндинг — чтобы «перецепиться» на порт, который реально
  стримит, а не на всегда-открытый служебный `8901–8904`). Возврат `true`, когда пошла
  телеметрия; `false` — если корутину отменили. Порога «применить всё равно» нет: если поток не
  идёт — дрон не подключён, слать нельзя (это и есть «не раньше»).
- **Bootstrap** (сейчас `awaitProxy → applyFcc`) заменить на:
  `if (awaitProxy(features) <= 0) return; if (!awaitLink(features)) return; applyFcc()` — затем как
  и раньше `homePointLoop`/`periodicLoop`. Лог: «keepalive: aircraft telemetry seen — applying FCC».
- **Один раз на каждый (пере)линк:** в idle-ожидании `homePointLoop` кроме фронта
  `HomePointMonitor.recorded` детектить и **фронт реконнекта по `LinkState`** (RX застоял
  `> STALE_MS`, затем возобновился). Любой из двух фронтов → одно `applyFcc()`, с существующим
  полом `HOME_POINT_DEBOUNCE_MS = 30_000`. Это покрывает релинк даже в помещении, где home-point
  не записывается. `periodicLoop` не трогаем (там свой read-verified путь).
- Новые константы: `LINK_STALE_MS = 4_000` (или вынести в `LinkState`). Остальные тайминги —
  прежние.

### 4. `MainActivity.kt` — только формулировки (без нового состояния)
Уточнить текст карточки «Keep FCC applied» в `buildServices()` (строка ~277) и подписи авто-старта,
чтобы честно отражать новое поведение: *«Отправляет полный пакет FCC в момент, когда дрон выходит
на связь (идёт телеметрия), и пере-применяет при релинке. Событийно, без холостого трафика».*
Существующий `autoKeepalive` + его авто-старт-свитч и `BootReceiver` уже обеспечивают
arm на запуске приложения и на загрузке пульта — **новый `AppState`-флаг не нужен** (иначе он
дублировал бы `autoKeepalive`).

### 5. `DiagServer.kt` — диагностика для верификации на железе
Добавить эндпоинт `/link` → `LinkState.statusJson()` (`{frames, ageMs, connected}`) и строку в
`/help`; по желанию — вывести в веб-дашборд рядом с `/homepoint`. Помогает на RC2 глазами
подтвердить «телеметрия пошла → только тогда applyFcc».

### 6. Тест `app/src/test/java/com/dji/fccgpsoff/LinkStateTest.kt`
Off-device (шаблон — `ForegroundGateTest`): с инъецированными часами проверить, что
`connected()` истинно в окне свежести и ложно после `STALE_MS`; что `onFrame()` считает кадры;
что детект фронта реконнекта срабатывает «застой→возобновление» и не срабатывает на непрерывном
потоке.

## Ключевые решения

- **Гейт по входящей телеметрии, а не по открытому порту** — прямой урок из `djiparam`
  (`rc331`: порт открыт, кадры молча теряются) и из критики «connect-by-open-port» FreeFCC.
- **Переиспользуем keepalive, а не заводим второй сервис/флаг** — режим `HOME_POINT` уже =
  «применить при подключении + пере-применять»; дублировать `autoKeepalive` новым `autoApplyFcc`
  смысла нет.
- **Правки минимальны и не трогают провод** — новый пассивный счётчик в RX-приёмнике и
  переупорядочивание триггера; байты/CRC/тайминги/порты неизменны.

   - Затем поднять дрон/DJI Fly до линка — как только пошла телеметрия (`/link connected:true`),
     в логе ровно один блок `applyFcc` (21 `TX p40009` ×2 + регуляторная запись), **после** строки
     «aircraft telemetry seen», не раньше.
   - Разорвать и восстановить линк → ещё одно применение (пол 30 с соблюдён), без шторма.
   - Ребут пульта с включённым авто-стартом → keepalive поднимается, ждёт телеметрию, применяет
     только после реального линка.
