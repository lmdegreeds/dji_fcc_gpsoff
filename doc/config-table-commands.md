# Config Table — полная группа команд доступа к параметрам FLYC

**Железо:** DJI RC 2 (`rc331`) + Lito X1 (`1581EXAMPLE000000000`), прошивка **v400**.
**Дата:** 2026-08-14. **Инструмент:** diag-server `http://<rc-ip>:8899/` (`/probe`, `/send`, `/params/*`).
**a11y:** включён, DJI Fly ни разу не на переднем плане (`readsAllowed:true`).

> **Условия замеров — читать перед тем, как опираться на числа.** Раскладки кадров и коды статусов
> снимались при **полностью остановленном** DJI Fly; числа надёжности и маршруты `03:FA` — при
> **запущенном в фоне**. Это разные режимы, и смешивать их нельзя: см. «Отвечаемость при живом Fly».

Приложение использует две команды доступа к параметрам — `03:F8` чтение и `03:F9` запись по хешу
имени. В таблице команд прошивки их **шесть**, плюс живое семейство by-index. Здесь — что из этого
реально отвечает на нашем железе, точные раскладки кадров и что это даёт приложению.

> **TL;DR.** Работают `F7` (метаданные по хешу: тип/ширина/min/max/default/имя), `FA` (сброс к
> дефолту, ровно один параметр), `E0` (атрибуты таблицы: 1594 записи, CRC) и `E1` (структура по
> индексу, с именем). Мертвы `FB` и `F0`. **Статус 3 у F7 = «такого параметра нет»** — это ответ, а не
> тишина, и он решает проблему имён Lito X1. `E0`+`E1` дают полный дамп каталога **без Param Studio**.
> Маршрут не изменился: отвечает только **40007 wrapped**, значит всё новое наследует тот же
> foreground-гейт и тот же риск для видео Fly.

## Матрица команд

Каждый запрос коррелирован **по seq** (см. «Методика» ниже) — без этого результаты недостоверны.

| Cmd | Имя | Результат | Чем подтверждено |
| --- | --- | --- | --- |
| `03:F7` | Get Param Info By Hash | **работает** | Полная структура. Сверено с экспортом Param Studio — 7 из 7 параметров совпали точно |
| `03:F8` | Read Param By Hash | работает | Уже используется (`ParamRead`); взят как базовая линия маршрута |
| `03:F9` | Write Param By Hash | работает | Уже используется (`ParameterAddress.write`) |
| `03:FA` | Reset Params By Hash | **работает** | Сбросил **ровно один** параметр: `forearm_led_ctrl` 0 → 239, LED загорелись (визуально). 6 соседних параметров не изменились |
| `03:FB` | Read Params By Hash | **молчит** | 5 раскладок payload, 0 ответов `03:FB` примерно в 1700 кадрах. Ни один клиент на шине её не использует |
| `03:FC` | Write Params By Hash | не тестировалась | Запись с недокументированной множественной раскладкой при работающей F9 — риск без выигрыша |
| `03:E0` | Get Tbl Attribute | **работает** | Таблица 0: **1594** записи, `entries_crc = 0x2ae1a5ad`. Таблицы 1–5 → статус 9 |
| `03:E1` | Get Item Attribute | **работает** | Структура по индексу, включая имя. 25 из 25 индексов ответили |
| `03:E2` | Get Item Value | бесполезна | Отдаёт `00000000` на любой индекс, включая заведомо несуществующий 1600 |
| `03:F0` | Get Param Info By Index | **молчит** | Команда набора 2015; борт отвечает по набору 2017 |

**Гибрид поколений.** By-hash команды (`F7`/`F8`/`F9`/`FA`) — из набора 2015, by-index (`E0`/`E1`) — из
2017, и на этом борту сосуществуют, при этом `F0` мёртв. Поколение определяется **покомандно**, а не
целиком — проверять надо каждую.

## Раскладки кадров

Маршрут для всего ниже: **wrapped 40007**, sender 2 → receiver 3, `cmd_type` 0x40 — тот же, что у
`ParamRead`. Смещения от начала payload, всё little-endian.

### `03:F7` Get Param Info By Hash

Запрос: `param_hash` (u32) — идентичен запросу F8.

```text
off  0  status     u8    0 = ok, 3 = такого параметра нет
off  1  type_id    u16   0=U8 1=U16 2=U32 3=U64 4=I8 5=I16 6=I32 7=I64 8=F32 9=F64
off  3  size       u16   ширина значения в байтах
off  5  attribute  u16   флаги; наблюдались 1, 3, 7 — СМЫСЛ БИТОВ НЕ ВЫЯСНЕН
off  7  limit_min  u32*
off 11  limit_max  u32*
off 15  limit_def  u32*
off 19  name       asciiz
```

`u32*` — union: 4 байта переинтерпретируются по `type_id`. F32 — IEEE-754; I8/I16/I32 — дополнительный
код с расширением знака (иначе `-1` типа I16 прочитается как 65535). Ровно та же логика, что уже
живёт в [`ParamCatalog.decode(v, typeName)`](../app/src/main/java/com/dji/fccgpsoff/ParamCatalog.kt).

Пример целиком, `forearm_led_ctrl`:

```text
tx  55cc3075 11000000 5511049202030840 03f7 4e9115f3 <crc>
rx  00 0000 0100 0700 00000000 ff000000 ef000000 666f726561726d5f6c65645f6374726c00
    │  │    │    │    │        │        │        └ "forearm_led_ctrl"
    │  │    │    │    │        │        └ def 239
    │  │    │    │    │        └ max 255
    │  │    │    │    └ min 0
    │  │    │    └ attribute 7
    │  │    └ size 1
    │  └ type_id 0 (U8)
    └ status 0
```

### `03:FA` Reset Params By Hash

Запрос: `param_hash` (u32) — как у F8.

```text
off  0  status      u8
off  1  param_hash  u32   эхо
off  5  new_value   size байт   значение ПОСЛЕ сброса
```

Ответ по форме совпадает с F8, но `new_value` — это значение, к которому сбросили. То есть FA за
**один round-trip** делает и запись, и подтверждение: `00 4e9115f3 ef` = «сбросил, теперь 239».

### `03:E0` Get Tbl Attribute

Запрос: `table_no` (u16).

```text
off  0  status       u16   0 = ok, 9 = нет такой таблицы
off  2  table_no     u16
off  4  entries_crc  u32
off  8  entries_num  u32
```

На Lito X1 v400: единственная таблица — 0, `entries_num = 1594`, `entries_crc = 0x2ae1a5ad`.
Заметьте: экспорт Param Studio того же борта содержит **953** параметра — то есть `entries_num`
считает и пустые слоты (см. статус 14 ниже), а экспорт только именованные.

### `03:E1` Get Item Attribute

Запрос: `table_no` (u16) + `param_index` (u16).

```text
off  0  status       u16
off  2  table_no     u16
off  4  param_index  u16
off  6  type_id      u16
off  8  size         u16
off 10  limit_def    u32*
off 14  limit_min    u32*
off 18  limit_max    u32*
off 22  name         asciiz
```

> **Ловушка.** F7 и E1 отдают одни и те же три лимита в **разном порядке**: F7 — min, max, def;
> E1 — def, min, max. Один общий декодер на обе команды молча перепутает дефолт с минимумом, и на
> U8-параметре с `min = 0` это будет выглядеть правдоподобно.

## Коды статусов

Выведены из поведения, не из документации.

| Код | `F7` (u8) | `E0` / `E1` (u16) |
| --- | --- | --- |
| 0 | ok | ok |
| 1 | — | payload короче 4 байт |
| 2 | — | индекс за пределами `entries_num` |
| 3 | **такого параметра нет** | — |
| 9 | — | нет такой таблицы |
| 14 | — | слот по индексу пуст (**не ошибка**) |

Как подтверждались: статус 3 — мусорными именами (`zzz_not_a_real_param_at_all`, `qqqqqqqqqqqq` —
оба дали 3, при положительном контроле 0); статус 9 — таблицей 5, которая даёт его и в E0, и в E1;
статус 2 — индексом 1600 при 1594 записях; статус 14 — тем, что индексы 20–21 и 34–44 дают его, а
22–33 в том же прогоне возвращают полные структуры.

## Отвечаемость при живом DJI Fly

Всё выше снималось при остановленном Fly. Рабочее условие приложения — Fly **в фоне**, и там картина
другая. Одно окно, одна попытка, 1500 мс, wrapped 40007, seq-корреляция, по 10 повторов:

| Команда | Fly остановлен | **Fly в фоне** | Кадров в окне (Fly в фоне) |
| --- | --- | --- | --- |
| `F7`, имя существует | ~100% | **70%** | med 204, min 6, max 589 |
| `F7`, имени нет (статус 3) | ~100% | **50%** | med 148 |
| `F8` чтение значения | ~100% | **70%** | med 58 |
| `E0` атрибуты таблицы | ~100% | **50%** | med 41 |
| `E1` по индексу | 25/25 | **40%** | med 27 |

**Маршрут не был артефактом остановленного Fly.** Гипотеза, что владельцем сессии тогда были мы и
поэтому ответы приходили, — опровергнута: с живым Fly они приходят, просто реже.

### Потери пооконные, а не покадровые — и это меняет выводы

Два прогона, 24 окна суммарно, **ни одного частичного результата**:

- **E7** — `F7` и `F8` на одно имя, оба кадра в один сокет: оба ответа в **11 из 12** окон, «только
  один» — **ни разу**.
- **E7b** — три **разных** параметра (набор `FlightState`: `forearm_led_ctrl`, `gps_enable`,
  `fswitch_selection`), три `F8` в один сокет: распределение строго **{0 ответов: 7, 3 ответа: 5}**.

Независимость при p = 0,70 предсказывала бы 49% и 34% соответственно, и обязательно давала бы
частичные окна. Их нет. ⇒ **окно либо отдаёт все ответы, либо ни одного**; добавление запросов в окно
не ухудшает шанс каждого из них.

**Как это соотносится с откатом `readMany`.** `doc/fcc-autoapply-tests.md` описывает симптом
«gps/fswitch часто мимо» при живом LED — то есть **частичный** результат, которого на шине не
бывает. Значит причина была не в шине, а в реализации; наиболее вероятный механизм —
`WrappedFrames.walk` останавливается на первом совпадении (`onFrame(inner)?.let { return it }`), так
что наивный батч систематически отдавал первый параметр и терял остальные. Это **не** реабилитирует
батч задним числом: `FlightState` работает и трогать его незачем. Но для нового кода объединение
запросов в окне — не запрет, а вопрос корректного сбора **всех** совпадений за один проход.

### Маршруты для `03:FA`

Цель `forearm_led_ctrl`, перед **каждым** запуском значение принудительно возвращалось в 0, чтобы
сброс к дефолту 239 был наблюдаем (иначе тест «сбрось то, что уже на дефолте» ничего не значит).

| Порт | Обрамление | sender / cmd_type | 1 выстрел | 3 повтора по 120 мс |
| --- | --- | --- | --- | --- |
| **40008** | unwrapped | 2 / 0x40 | **сработала** | сработала |
| 40009 | unwrapped | 130 / 0x20 | нет | **сработала** |
| 40009 | unwrapped | 2 / 0x40 | нет | **нет** |
| 40007 | wrapped | 2 / 0x40 | нет | **сработала** |

Три вывода:

1. **`FA` принимается на всех трёх портах** — одиночные промахи были доставкой, а не маршрутизацией.
2. **На 40009 обязательна identity пульта** (sender 130, `cmd_type` 0x20): с sender 2 команда не
   действует даже с повторами. Это ровно правило из `ParameterAddress.senderFor()`/`ctFor()` — оно
   оказалось нагруженным, а не косметическим.
3. **Практический выбор — 40008**: сработала с одного кадра, это уже штатный порт записи приложения,
   и он не несёт видео Fly. Ответ там не возвращается, поэтому подтверждение читается отдельным `F8`
   на 40007.

### Полный обход таблицы по `03:E1` — замер

Глубина 32 запроса в одно окно, до 4 проходов с добором. **DJI Fly остановлен.**

```text
1594 из 1594 разрешено за 102 с, unknown = 0
named 881 · empty 713 · проходов 4
```

Сверка с зашитым в APK `litox1.json` (953 записи):

| | Кол-во | Проверка |
| --- | --- | --- |
| есть и там, и там | 859 | **857 полностью идентичны** по типу/min/max/default; оставшиеся 2 — разница печати F32 (`-9999.900390625` против `-9999.9`), тот же битовый шаблон |
| только в каталоге | 94 | выборка из 8 случайных — **8 из 8** дали `03:F7` статус 3, то есть на борту их нет |
| только на борту | 22 | зашитый каталог их не содержит |

⇒ **Каталог из APK для этого борта одновременно лишний на 94 записи и неполный на 22.** Дамп с
борта точнее. И это же — исчерпывающая проверка ловушки порядка лимитов: при перепутанных
`min`/`def` совпадений было бы почти ноль, а не 857 из 859.

Результат пишется в форме v1 `.dhp` и грузится существующим `ParamCatalog.load` без нового
парсера: `board-<serial>.dhp` в `filesDir/param_tables/`.

### Поле `attribute`

| Параметр | Каталог | `attribute` |
| --- | --- | --- |
| `g_status.user_info.statistical_info.total_*` (4 шт.) | read-only (`min==max`) | **0** |
| `multi_mixer_type` | read-only (`min==max==1`) | **3** |
| `gps_enable`, `ce_regulatory_level` | writable | 3 |
| `forearm_led_ctrl`, `max_height`, `fswitch_selection` | writable | 7 |

`attribute == 0` совпадает со счётчиками `g_status.*`, но `multi_mixer_type` показывает, что
«запаянный диапазон» и `attribute` — **разные** признаки. Значений больше, чем в выборке: при
полном обходе встретилось и `attribute 9` (`battery_type`, U8 0…4). ⇒ **показывать, но не гейтить
на нём запись.**

## Проблема имён Lito X1 — решается

[`PROTOCOL.md`](PROTOCOL.md) описывает её как неразрешимую: «писать все кандидаты и смотреть, кто
ответит, здесь не работает, потому что чтения не маршрутизируются обратно — “нет ответа” означает
“нет маршрута”, а не “отсутствует”». Отсюда ручной тумблер **Lito X1 / Other DJI** в
[`ParameterAddress`](../app/src/main/java/com/dji/fccgpsoff/ParameterAddress.kt).

F7 это снимает: статус 3 — **ответ** борта «такого параметра нет».

| Логический параметр | Имя | F7 | Тип / диапазон / дефолт |
| --- | --- | --- | --- |
| REGULATORY | `ce_regulatory_level` | **0** | U8 · 0…255 · def 255 |
| REGULATORY | `c1_regulatory_restriction` | **3** | нет на этом борту |
| FOREARM_LED | `forearm_led_ctrl` | **0** | U8 · 0…255 · def 239 |
| FOREARM_LED | `g_config.misc_cfg.forearm_lamp_ctrl` | **3** | нет на этом борту |
| GPS_ENABLE | `gps_enable` | **0** | U8 · 0…1 · def 1 |
| GPS_ENABLE | `g_config.gps_cfg.gps_enable` | **3** | нет на этом борту |

Три пары из трёх разделились чисто. Тумблер профиля может стать автоопределением: по одному F7 на
кандидата.

**Про суффикс `_0`.** Хеш считается по `name + "_0"`, но **каноническое имя борта — без суффикса**:
F7 на хеш от `forearm_led_ctrl_0` возвращает строку `forearm_led_ctrl`. Суффикс участвует только в
хешировании. (Совпадает с `flyc_parameter_compute_hash` из dji-firmware-tools, где `_0` уже входит в
имена их таблиц.)

## Состояние борта на момент замеров

Значения — через F8, дефолты — через F7.

| Параметр | Сейчас | Дефолт | Чтение |
| --- | --- | --- | --- |
| `ce_regulatory_level` | 255 | 255 | на дефолте → **FCC не применён** |
| `ce_country_type` | 36 | 0 | это FCC-значение (`0x24`) |
| `g_config.flying_limit.max_height` | 500 | 120 | поднято профилем FCC; 500 — ровно объявленный максимум |
| `gnss_region_mode` | 0 | 0 | на дефолте |
| `fswitch_selection` | 3 | 12 | ATTI; диапазон шире ожидаемого — **0…21** |
| `sdr_lost_prevent_never_takeoff_en` | 1 | 1 | на дефолте |
| `sdr_lost_prevent_has_takeoff_en` | 1 | 1 | на дефолте |

Картина рассогласованная: `ce_country_type` и `max_height` несут следы FCC, а `ce_regulatory_level` и
`gnss_region_mode` вернулись к дефолтам — ровно то, что PROTOCOL.md описывает фразой «DJI Fly
перезаписывает CE при каждом релинке», и аргумент в пользу keepalive.

Заодно: `max_height = 500`, которые ставит кадр 3 профиля FCC, — это **не произвольное число, а
объявленный самим FC максимум** для этого параметра.

## Индексы плывут между прошивками, имена — нет

Два экспорта **одного и того же аппарата**, v300 и v400:

| Имя | idx fw300 | idx fw400 | Сдвиг |
| --- | --- | --- | --- |
| `forearm_led_ctrl` | 23 | 23 | не двинулся |
| `ce_country_type` | 239 | 49 | −190 |
| `g_config.flying_limit.max_height` | 264 | 76 | −188 |
| `fswitch_selection` | 146 | 133 | −13 |
| `gps_enable` | 650 | 382 | −268 |
| `ce_regulatory_level` | 1297 | 1208 | −89 |

Решение адресоваться по имени, а не по индексу, подтверждается количественно. Практическое следствие:
каталог, собранный обходом по индексу, **привязан к прошивке** и должен инвалидироваться при её
смене. Ключ для этого — `entries_crc` из E0.

## Методика: корреляция по seq обязательна

DJI Fly опрашивает те же команды на той же шине. Матч только по `cmd_set`/`cmd_id`/`isResponse`
возвращает **чужой ответ**: во втором прогоне идентичные запросы `03:E1` с payload `00000000` давали
то `0100`, то `0e00`. После добавления сверки `seq` (FC эхом возвращает sequence запроса)
результаты стали строго детерминированными.

`ParamRead.extract` сегодня выживает только потому, что сверяет **эхо-хеш**. У `E0`/`E1` хеша в
ответе нет — если их добавлять, сверка по seq обязательна. `WrappedFrames.Inner` уже отдаёт `seq`
наружу.

**Окна должны быть щедрыми.** В первом прогоне F7 был объявлен отсутствующим при 3 попытках по 1,5 с —
и оказался живым при 6. Любая проверка «есть ли параметр» с коротким бюджетом будет выдавать ложные
отрицания, то есть ровно тот отказ, который приложение уже документирует.

## Что НЕ сработало

- **`03:FB` Read Params By Hash** — молчит. Проверены раскладки: `hash1‖hash2`, `count:u8‖hashes`,
  `count:u16‖hashes`, одиночный `hash`, `count:u8‖hash`. Ноль ответов `03:FB` примерно в 1700 кадрах
  суммарно, включая чужие. Похоже, множественные формы на этой прошивке не реализованы вовсе.
- **`03:F0` Get Param Info By Index** — молчит (набор 2015 при живом наборе 2017).
- **`03:E2` Get Item Value** — отвечает `00000000` на любой payload длиной 4–5 байт, включая индекс
  1600, которого не существует. Не отдаёт значений; payload <4 байт → статус 1, ≥6 байт → статус 3.
- **Чтение на 40008 и 40009** — на 40008 окно чтения дало **ноль кадров** (чистый sink на запись);
  40009 кадры несёт, но нашего ответа в них нет. Проверено и для F7, и для F8, в bare и wrapped
  обрамлении, с обеими комбинациями sender/cmd_type. **Ответ на F7/E0/E1 возвращается только на
  40007 wrapped.**
  Различать надо две вещи: *команда доходит* и *ответ возвращается*. У `FA` доходит на всех трёх
  портах (таблица маршрутов выше), а возвращается ответ по-прежнему только на 40007 — поэтому сброс
  через 40008 подтверждается отдельным `F8`.
- **Первый прогон F7** — ложное «no reply» из-за бюджета в 3 попытки (см. выше). Записано отдельно,
  потому что это тот же класс ошибки, который может испортить автоопределение профиля.

## Что это даёт приложению

Ниже — предложения, **в коде ничего не менялось**. По убыванию отношения пользы к риску.

1. **Автоопределение профиля имён вместо тумблера.** По одному F7 на кандидата при появлении борта.
   Сейчас неверно выставленный тумблер превращает *каждую* запись в молчаливый no-op, и отличить это
   от «команда прошла» нельзя. Трогает `ParameterAddress`, `AppState`.
2. **Метаданные с борта вместо файла каталога.** F7 убирает ветку «unknown width — refuse» в
   `ParamCatalog.encodeChecked` (ширина приходит с борта, а не угадывается по `max`), чинит
   знаковые/float-чтения без экспорта и позволяет проверять диапазон по лимитам **борта**, а не файла.
   Цена — +1 round-trip на чтение параметра.
3. **Настоящий reset через `03:FA`.** Комментарий в
   [`DiagServer.resetParam`](../app/src/main/java/com/dji/fccgpsoff/DiagServer.kt) утверждает, что
   отдельного DUML-опкода reset не существует — **это неверно**. FA берёт дефолт **борта**, а не
   чужого экспорта. Отправлять на **40008** тем же транспортом, что и `03:F9` сегодня (sender 2,
   `cmd_type` 0x40, 2–3 повтора) — новый маршрут не нужен, видео не затрагивается; подтверждение —
   отдельный `F8` на 40007.
4. **Полный дамп каталога с борта через E1.** Обход `0 … entries_num−1` даёт имена, типы, лимиты и
   дефолты — каталог собирается с аппарата, без Param Studio и без файла. Значения дочитываются по
   хешу через F8. Работает и на незнакомом борте. Кэш-ключ — `entries_crc` + `entries_num` из E0.
   **Цена измерена только на стенде:** он дал 2,17 с/индекс (HTTP + отдельный TCP-сокет + окно
   900 мс на запрос) → ~58 мин на 1594. Внутри приложения, на удерживаемом сокете с конвейером, будет
   заметно быстрее, но насколько — неизвестно; 58 минут это **верхняя граница, а не оценка**.
5. **Корреляция по seq** — предусловие для п. 4 (см. «Методика»).
6. **Отпечаток прошивки.** `entries_crc` + `entries_num` идентифицируют сборку таблицы. Достаточно,
   чтобы предупредить «загруженный экспорт снят не с этого борта» — сейчас ничто этого не проверяет,
   а `/params/reset` в таком случае молча запишет чужой дефолт.

**Чего это не решает.** Маршрут не изменился — всё новое идёт через 40007 и наследует foreground-гейт
и риск подвесить видео Fly на 1–2 с. Ничего из перечисленного не делает чтения безопаснее, только
полезнее.
